1. 這個專案在做什麼？核心研究問題與理論背景
AI 歷史助教 vs. 歷史人物角色扮演 × 自由聊天 vs. 錯誤引導學習 (EBL)

研究動機：傳統死背 vs. 歷史學家思維

歷史教育長久以來的痛點在於學生容易落入「死記年代與片面結論」的框架，缺乏像歷史學家一樣「檢視史料證據、理解歷史脈絡、釐清多元因果、換位思考立場」的高階歷史思維能力 (Historical Thinking, van Drie & van Boxtel, 2008)。

生成式大型語言模型 (LLM) 具備強大的語意理解與對話能力，但若只是給學生一個無約束的聊天機器人，學生往往只是索取標準答案。本專案 (Histosphere) 旨在打造一個嚴謹受控的線上實驗平台，探討不同 AI 介入策略對學習者歷史思維與概念重構的具體成效。

兩大研究自變項 (Independent Variables)

  • 自變項 1：教學引導策略 (Instructional Scaffold) — Standard Chat（自由對話，學生提問 AI 自然回答）對比 Historical Error-Based Learning (EBL)（從學生答錯的任務出發，主動引導學生自主發現錯誤、檢視證據並修正推論）。
  • 自變項 2：AI 互動身分 (Agent Persona Mode) — Generic Assistant（客觀中立的 AI 歷史助教）對比 Historical Persona Role-Play（AI 扮演事件當事人，以第一人稱視角、受限於該時代知識邊界進行沉浸式對話）。
白話比喻
就像在歷史博物館裡：你身邊可以是一位隨時回答問題的導覽員 (Generic)，也可以是一位穿越時空來到你面前的歷史人物本人 (Persona)；而他們的教學方式，可以是隨便你問他答 (Standard)，也可以是看到你寫錯學習單時，一步步反問你、帶你找線索 (EBL)。

2. 四種實驗條件（2×2 矩陣設計）
嚴謹的受控因子分配：Condition 01 至 Condition 04

在系統後端（app/core/experiment_conditions.py），每個條件都被定義為一個不可變的 ExperimentConditionDefinition 資料類別，嚴格綁定系統行為旗標，杜絕實驗變數漂移：

CONDITION 01 對照組
一般 AI 助教 ＋ 自由對話
AI 作為客觀助教，學生可自由提問歷史背景。AI 自然回答，不主動追蹤學生題目錯誤，亦不主動執行 EBL 引導。
ebl_enabled: false | roleplay: false
agent_mode: generic | policy: standard
CONDITION 02 EBL 組
一般 AI 助教 ＋ EBL 引導
AI 作為蘇格拉底式助教，主動鎖定學生答錯的填空題，逐步引導學生檢視證據、推理因果與自我修正。
ebl_enabled: true | roleplay: false
agent_mode: generic | policy: scaffold
CONDITION 03 角色扮演組
歷史人物 ＋ 自由對話
AI 扮演事件當事人（如林獻堂）以第一人稱對話，具備時代知識邊界與主觀立場，但不會主動針對作答錯誤進行教學引導。
ebl_enabled: false | roleplay: true
agent_mode: persona | policy: standard
CONDITION 04 全功能實驗組
歷史人物 ＋ EBL 引導
AI 以歷史人物當事人身分，結合自身處境與關切點，引導學生反思填空題中的迷思概念，展開深度歷史思維探究。
ebl_enabled: true | roleplay: true
agent_mode: persona | policy: scaffold
實驗控制關鍵：Role-Play 僅作為 Renderer
為了防止「角色扮演的講話字數或額外提示」破壞實驗公平性，系統將 Persona 設定為純渲染層 (Renderer Only)：在 Condition 04 中，AI 提供的證據預算 (Evidence Budget)、問題數量、揭露層級必須與 Condition 02 完全一致，僅有「說話人稱與身分語氣」不同。

3. 學生的完整操作體驗與階段生命週期
登入 → 歷史閱讀 → 填空題作答 → 非同步評分 → 5分鐘倒數對話 → 結算
1
受測者登入 (Auth Login)
學生使用研究者預先在 Supabase Auth 建立的專屬帳號登入。系統驗證 JWT 後，從 participants 表綁定 participant_code 並載入該受測者被指派的條件列表。
2
瀏覽歷史事件 (Event Hub)
首頁展示當前開放的歷史事件（如：臺灣議會設置請願運動）。實驗控制設計：學生端刻意隱藏事件長文介紹（避免提前閱讀干擾實驗），僅顯示事件年代、分類與插圖。
3
建立實驗 Session 與狀態快照 (Session Creation)
點擊進入事件時呼叫 POST /api/sessions。後端建立 session，並將當前的條件設定完整快照至 condition_snapshot。這保證即使後續管理員修改條件定義，已進行中的 session 永遠不受影響。
4
歷史文本填空作答 (Task Attempt)
學生閱讀嵌入題目 Token（如 {{blank:q01}}）的歷史敘事文本，完成填空題、選擇題或是非題。支援草稿自動暫存。點擊送出後觸發 POST /api/tasks/{id}/submit。
5
非同步評分與迷思概念分析 (Async Evaluation - 202 Pattern)
後端立即回傳 202 Accepted。背景執行雙軌評分：客觀題使用確定性比對 (Exact & Normalized match) 評定對錯，並同時調用 LLM 生成每題錯誤的迷思概念分析 (Misconception Enrichment)。前端透過輪詢查詢狀態。
6
5 分鐘 AI 對話探究 (Chat Interaction Phase)
進入聊天室，若為角色扮演組，AI 會自動生成一段沉浸式開場白。同時啟動 5 分鐘嚴格倒數計時（時間戳記 timer_ends_at 存於資料庫）。學生每送出一則訊息，後端即執行一次嚴格的 Prompt 組裝與驗證。
7
中斷恢復機制 (Fault-Tolerant Reconnection)
若學生中途斷線或重新整理瀏覽器，前端呼叫 GET /api/sessions/current，自動根據當前階段（作答中、評分中、對話中）恢復畫面，倒數計時器亦沿用原時間戳記，不會重新計算。

4. Prompt 組裝管線 (PromptService)
12 個模組的嚴格組裝順序、動態白名單與隱私遮蔽

運作原理：模組化動態拼裝 (Prompt Composition)

在 app/services/prompt_service.py 中，系統不使用單一死板的字串模板，而是將 Prompt 拆解為 12 個具備單一責任的 PromptModule。在每次學生發送訊息時，根據實驗條件快照與當前狀態機進度動態拼接：

# 模組名稱 (Module) 具體職責與注入內容 條件啟用
1 general_prompt 全域論文實驗規範：要求繁體中文、歷史真實性優先於流暢度、嚴禁捏造史實/引用/私人想法、離題處理規範 (off_topic_redirect=true)。 全條件
2 independent_2_prompt 教學模式指令：宣告當前為 Standard Chat 自由模式或 EBL 引導模式。 全條件
3 event_context 事件基礎背景：事件標準名稱、世紀、起始/結束年份、事件歷史脈絡描述。 全條件
4 learner_task 學生作答結果：EBL 模式下注入所有答錯題目的作答紀錄；Standard Chat 模式下僅注入簡要題幹（不含標準答案）。 全條件
5 interaction_runtime EBL 狀態機指令：當前鎖定題目、允許之 Dialogue States、允許之 Disclosure Levels、前次嘗試次數。
關鍵安全設計：expected_answer 被強制遮蔽為 "SERVER_SIDE_HIDDEN"。		 02, 04
6 conversation_history 歷史對話上下文：每則限制 1,600 字元，總預算上限 16,000 字元。超出時自動裁切最舊訊息。 全條件
7 independent_1_prompt AI 身分指令 (Renderer)：Generic 模式宣告為 AI Tutor；Persona 模式要求以第一人稱（我、我們）發言，嚴禁跳出角色。 全條件
8 persona_event_context 人物情境設定：人物說話口吻、社會身分、事件觀察視角、時間邊界與知識截斷年 (knowledge_cutoff_year)。 03, 04
9 source_context RAG 史料文本檢索注入區（支援史料佐證引用）。 動態
10 turn_intent 當前回合意圖：區分是開場白 (opening) 還是常態多輪對話 (conversation)。 全條件
11 runtime_policy JSON 結構化輸出協議：要求 LLM 輸出特定 JSON Schema（包含 visible_reply, internal_reasoning 等）。 全條件
12 user_message 學生最新發送之對話訊息。 全條件

5. EBL 引導機制與六大推理階段 (State Machine)
從錯誤出發：ELICIT → INSPECT → CONTEXTUALIZE → REVISE → REFLECT → RESOLVED

核心理念：錯誤導向學習 (Error-Based Learning)

當學生在條件 02 或 04 進行對話時，後端狀態機（app/core/historical_ebl_policy.py）會主動從 task_attempt 中挑出第一個未解決的錯誤題目作為 InteractionTarget，依序引導學生經歷六個認知階段：

S1
ELICIT_REASONING (引出既有推論)
AI 目標：探詢學生的初始想法。「你原本寫了這個答案，可以說說你當時是根據什麼理由判斷的嗎？」
學生動作：陳述原始主張與其背後的推論邏輯。
S2
INSPECT_EVIDENCE (檢視史料證據)
AI 目標：引導學生回頭檢視文本中的關鍵線索。「這份史料裡提到了一段話，你覺得這段記載支持還是削弱了你的答案？」
學生動作：找出文本證據，評估其關聯性。
S3
CONTEXTUALIZE_OR_COMPARE (脈絡化與比較)
AI 目標：套用特定歷史思維維度（因果關係、時代脈絡、變遷與延續、歷史觀點）。「如果考慮到當時總督府的統治政策轉變，這件事的起因會是什麼？」
學生動作：將證據置入具體歷史情境進行深度辨析。
S4
REVISE_CLAIM (修正主張)
AI 目標：要求學生以「主張-證據-推理」(Claim-Evidence-Reasoning, CER) 結構重寫答案。「結合你剛才發現的線索，你會想如何修正原本的答案？」
學生動作：提出修正後的歷史論點。
S5
REFLECT (後設認知反思)
AI 目標：促發後設認知反思。「比較你最初和現在的想法，是什麼證據讓你改變了觀點？」
學生動作：回顧自己的思考轉折點。
S6
RESOLVED (問題解決與過渡)
AI 目標：確認概念修正完成。若題目列表中還有其他未解決的錯誤，自動橋接 (Bridge) 至下一個目標題目；若已無錯誤則總結對話。
狀態機轉移嚴格約束 (EBL_STATE_TRANSITIONS)
狀態機只允許「停留在當前狀態繼續引導」或「順向推進至下一個狀態」。嚴禁跳級（如直接從 S1 跳到 S4）或任意逆流。若 LLM 輸出了非法的狀態跳躍，後端驗證層會立即攔截並觸發重試。

6. 漸進式提示揭露階層 (D0–D4 Disclosure Hierarchy)
嚴格控制資訊釋出：禁止 AI 提早暴雷的硬性天花板

運作原理：步進式提示天花板 (Progressive Scaffolding)

為了避免 AI 在學生稍微卡關時就直接把答案說出來，系統設計了五級資訊揭露天花板 (Disclosure Levels)（app/core/interaction_contract.py）。每一輪對話中，AI 最多只能升降 1 級（Previous Level ± 1）：

D0
只問不給 (Restate & Elicit Only)
AI 只能重述學生剛才講過的話，並詢問其思路。完全不能主動補充任何新的史實、年代、人物或線索。
🚫 Hard Ceiling：僅能使用學生已說出的事實，嚴禁新增任何新資訊。
例：「你提到你認為是 1925 年成立的，能分享一下你是根據哪裡的印象做出這個推論的嗎？」
D1
指引方向 (Point to Location/Relation)
可以告訴學生「去看哪裡」（例如指向某段史料、某個年份區間、或某位人物），但絕對不能說出該處寫了什麼內容。
🚫 Hard Ceiling：只能指出檢查位置，不得轉述或引用證據文字、因果結論或答案同義詞。
例：「你有沒有注意到在故事第一段提到蔣渭水在臺北的那段敘述？那裡有一個關鍵時間點。」
D2
提供單一線索 (Provide One Evidence Clue)
允許 AI 從史料中精確引用一條具體線索或事實讓學生自行評估，但依然不能幫學生做結論。
🚫 Hard Ceiling：僅限單一客觀線索，不得幫學生完成論證句子。
例：「史料記載：『1921年10月，臺灣文化協會於大稻埕召開創立大會』。這項記載和你寫的年份有何差異？」
D3
提供比較框架或排除錯誤 (Two Clues / Comparison Frame)
可提供兩條線索、給予句式骨架 (Sentence Stem)、或明確排除一個錯誤方向。
🚫 Hard Ceiling：依然嚴禁替學生完成整句「主張-證據」推論。
例：「我們可以把 1920 年的市街庄制改革，與 1921 年文協創立對照。1925 年已是後期的治安警察法時期，因此可以排除 1925 這個選項。」
D4
強力結構引導 (Strongest Scaffolding - Blank Remains)
整理並排列所有最完整的佐證脈絡，唯獨將關鍵答案留白，由學生完成最後一步填答。
🚫 Hard Ceiling：即使學生多次失敗，在狀態進入 RESOLVED 之前，全系統任何層級皆嚴禁說出完整答案或同義詞。
例：「所有史料均指出：在大正十年、也就是民國十年的 10 月，這個協會在臺北創立。換算成西元的話，應該是 192＿ 年？」
技術核心：Source Withholding 與 Server-Side Hidden
當後端評估當前回合允許的最高揭露層級 prompt_disclosure_ceiling < D2 時，傳送給 LLM 的 Prompt 中 task_source_text 會被替換為 "WITHHELD"。這代表AI 在 D0 和 D1 時連史料原文都拿不到，從物理架構上杜絕 LLM 不小心把史料字句唸給學生的可能性！

7. 歷史人物角色扮演協議 (PersonaPromptProfile)
第一人稱視角、時代知識截止年、禁止全知視角與時代錯置

運作原理：嚴格的本體論知識邊界 (Epistemic Boundaries)

在 app/core/persona_prompt_contract.py 中，每個歷史人物都透過 PersonaPromptProfile 結構定義其嚴格的認知與語言邊界：

屬性欄位 設計意義與約束行為
speaking_style 說話口吻與語氣：例如「日治時期知識份子之文雅措辭、夾雜台語典故與漢詩素養」。
forms_of_address 對受測者之稱呼：如「青年朋友」、「同胞」、「仁兄」，嚴禁現代課堂用語（如「各位同學」）。
knowledge_cutoff_year 知識截止年份：如設定為 1930。人物絕不可能知曉 1930 年之後的事物（如二戰結束、國民政府來台）。
firsthand_experience_scope 親身經歷範疇：定義該人物真正親身參與的場合（如議會請願團）。未經授權的事件只能以「聽聞」或「不知」表述。
forbidden_claims 絕對禁止事項：嚴禁時代錯置 (Anachronism)、嚴禁全知歷史學家口吻、嚴禁宣稱非親歷之第一手見聞。
stance 主觀歷史立場：保留人物自身的政治抱負與局限性（例如溫和請願路線 vs 激進左派之辯）。
案例示範：學生詢問未來事件
若學生向 1920 年代的林獻堂詢問：「第二次世界大戰最後是誰打贏了？」
合規回覆：「閣下所言之『第二次大戰』，老夫實不知所指。現今乃大正年間，歐陸大戰方歇，我輩唯願帝國憲政之下，臺人能獲自治之權⋯⋯」
違規攔截：若 AI 回答了二戰歷史，驗證層會標記 persona_temporal_boundary_violation 並直接重試！

8. LLM 結構化輸出、雙層驗證與自我修復
JSON Schema 輸出、白名單驗證器、自動修復引擎與 Remediation 重試

1. 完整 JSON 輸出規範

後端要求 LLM 回應必須是嚴格符合以下 Schema 的 JSON 物件，將「給學生看的話」與「AI 的心智狀態與決策理由」完全拆離：

{
  "visible_reply": "同學，你剛才提到 1925 年成立，可以回想一下當時推動請願的第一波浪潮是在哪一年嗎？",
  "internal_reasoning": "學生答案年份偏晚。當前處於 ELICIT 階段，揭露等級維持 D0，先探詢其原始線索來源。",
  "dialogue_state": "ELICIT_REASONING",
  "dialogue_move": "reasoning_probe",
  "disclosure_level": "D0",
  "disclosure_reason": "學生尚未展開任何推論說明，依策略維持 D0 最低揭露。",
  "learner_progress": "no_progress",
  "off_topic_redirect": false,
  "completion_status": "continue",
  "annotations": ["historical_context"]
}

2. 驗證與修復管線 (Validation & Self-Healing Pipeline)

A
JSON 格式容錯修復 (json_runner.py)
若 LLM 輸出帶有 Markdown Code Fence（```json）、缺少尾部引號、或有多餘逗號，修復引擎會自動進行字串清洗與 AST 修復，無需消耗額外 API Token 重試。
B
業務合約嚴格檢查 (validate_completion_candidate)
檢查 7 大項目：狀態是否在允許列表、Move 是否匹配 State、Disclosure 是否超過 ±1 級、問題數是否超過 2 個 (MAX_FOCUSED_QUESTIONS_PER_TURN)、是否提前暴雷 (early_answer_exposure)、Persona 是否包含第一人稱、是否洩漏內部變數名稱 (internal_condition_leak)。
C
附帶補救指引重試 (RETRY_REMEDIATION)
若驗證失敗，後端不會直接報錯，而是將具體的修復指令 (Remediation) 附加至 Prompt 重新呼叫 LLM（最多 3 次，MAX_CHAT_GENERATION_ATTEMPTS = 3），確保系統在無人值守實驗中的高可用性。

10. 前後端架構與後端四層分層設計
Nuxt 3 ＋ FastAPI ＋ Supabase ＋ 後端清晰的依賴反轉架構

後端四層架構 (Clean Layered Architecture)

1
API Layer (app/api/v1/endpoints/)
10 個路由器模組（admin, chat, conditions, conversations, events, participants, personas, sessions, tasks 等）。負責 HTTP 協議解析、JWT/Admin 認證依賴注入 (deps.py)、請求 Schema 驗證。
2
Service Layer (app/services/)
15 個核心業務服務（ChatService, PromptService, TaskService, SessionService, ConversationService 等）。負責跨模組業務流程編排與對話生命週期控管。
3
Core Layer (app/core/)
純粹的實驗領域核心（experiment_conditions.py, interaction_contract.py, historical_ebl_policy.py, persona_prompt_contract.py）。無任何框架依賴，作為實驗規則與狀態機的唯一真理來源 (Single Source of Truth)。
4
Data & Provider Layer (app/db/, app/crud/, app/providers/)
以 RepositoryProtocol 抽象介面解耦資料存取。提供 SupabaseRepository 正式資料庫實作與 InMemoryRepository 高速測試實作；透過 LLMProvider 介面包裝 LiteLLM。

12. 安全防護、併發控制與容錯機制
Concurrency Guard (409)、冪等性 ID、學生訊息持久化優先、離題防護

高可靠性架構設計重點

1
單一操作併發保護 (Concurrency Guard - HTTP 409)
同一對話在同一時間只允許一筆處理中的 Operation。若學生在 AI 回覆前連續點擊發送，第二個請求會立即被後端攔截並回傳 409 Conflict，徹底防止 LLM 狀態機產生 Race Condition。
2
請求冪等性保護 (Idempotent client_request_id)
前端每次送出訊息皆攜帶唯一的 UUID (client_request_id)。若因網路抖動重發相同請求，後端直接回傳已完成的訊息，絕不會重複調用 LLM 或產生重複扣款。
3
學生訊息持久化優先 (Learner-First Durable Write)
在呼叫外部 LLM API 之前，學生的訊息必須先成功寫入資料庫。即便後續 LLM API 發生 500 錯誤或伺服器斷電，學生的對話紀錄永遠不會丟失，重新整理後即可直接手動點擊重試。
4
伺服器重啟自動復原 (Backend Restart Recovery)
若後端在處理 LLM 期間重啟，系統啟動時會自動掃描所有卡在 processing 的 Operation，並安全標記為 failed_retryable。學生端會立即出現「重試」按鈕，無需重新整理整個頁面。
5
離題防護與事件重新錨定 (Off-Topic Redirection)
若學生故意詢問與歷史事件完全無關之問題（如：寫一段 Python 程式碼），LLM 會輸出 off_topic_redirect=true。系統不會回答該問題，而是以角色身分優雅地將話題拉回事件當下，且不會扣減學生的提示次數或推進狀態機。
