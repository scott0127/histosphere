不可破壞的規則

這些不是實作偏好，而是資料可信度與實驗條件的邊界。

禁止用 hard delete 清理研究資料

Event、Persona、Participant、Session 與 Conversation 以封存或狀態轉換處理。任何資料刪除需求都必須先確認研究資料是否仍需追溯。

身分由後端決定

Learner 的 user_id 一律取自已驗證 JWT，不能信任前端 localStorage、query string 或 request body 傳來的身分。

Condition 必須 fail closed

找不到 participant、未分派該 Condition、順序不符或 participant 非 active 時，拒絕建立 Session，不能偷偷套用預設 Condition。

Session 是研究資料主軸

一個 Session 最多一份 task_attempt 與一段 conversation。重整只恢復，不建立第二份。

素材先鎖定再收案

Learner 只能開始已鎖定的 Event。鎖定前會驗證 Task 格式與唯一啟用 Persona；鎖定後禁止修改素材。

正式模型不可自動切換

一次實驗固定使用 LLM_MODEL。暫時性錯誤可重試同一 provider/model，但不得切換 provider 造成處遇不一致。

Admin test 不進正式匯出

管理員測試 Session 以 is_admin_test 分類，排除於 Learner 進度與正式研究匯出。

Learner 完整流程

每一步都持久化；頁面重整後由後端狀態決定返回哪一階段。

  1. Supabase Auth 登入

    Frontend 取得 access token；後端向 Supabase Auth 驗證 token，使用 JWT subject 作為唯一 Auth user id。

  2. 讀取 participant 與進度

    GET /api/participants/me 與 GET /api/sessions/progress 回傳後端認定的 participant、Condition 順序與既有 Session。

  3. 初始化或恢復 Event

    POST /api/event/initialize 檢查 participant assignment、執行順序、Event 封存與素材鎖定。已有未完成 Session 時直接恢復。

  4. 作答 Error-Elicitation Task

    草稿寫進唯一的 task_attempts row。送出後立即回傳 202 + attempt_id，前端輪詢處理狀態。

  5. Judge 與開場持久化

    後端以規則判客觀答案、LLM 判理由，建立逐題錯誤資料，再生成開場並建立唯一 Conversation。

  6. 五分鐘 Chat

    倒數只在 Conversation 與開場都可用時開始。每輪先保存 Learner 訊息，再呼叫 LLM，完成後保存 AI 訊息與 metadata。

  7. 時間到

    Session 轉為 completed，Learner 看到「本階段已結束」並進入下一階段；沒有 Learner 手動提前完成按鈕。

Session 與中斷恢復

Session 將 participant、Condition、Event、Task、Conversation 與計時器串成一條研究資料鏈。

initialized已建立 Session，進行 Task
attempt processingTask 已持久化，背景判題與開場生成中
conversation_startedChat 可用，五分鐘計時中
completed時間到或後端完成條件成立
archivedAdmin 重開時保留舊 Session
情境後端行為不應發生
Task 中重新整理讀取同一 Session 與同一 Attempt 草稿建立第二份 Attempt
判題中重整輪詢同一 attempt_id；必要時重新排程 processing job重新產生另一份 Session
Chat 中重開載入 DB 對話與原本 timer_ends_at，倒數不重置回到完整五分鐘
時間已到後重開後端懶惰檢查或 timer worker 將 Session 完成繼續送出 Chat
同 Event 已完成Learner 永久禁止再開；Admin 可 archive 舊 Session 並建立新 SessionLearner 自行重做
資料庫層保證 cardinality

task_attempts.session_id 與 conversations.session_id 都有唯一 index 且不得為 NULL；Application 層的「先查再建」不是唯一防線。

Error-Elicitation Task 與 Judge

Task 是產生後續學習機會的媒介，不是前測、後測或 Historical Thinking outcome score。

Authoring contract

error_elicitation_task_full_text 保存完整閱讀材料與 {{blank:qNN}} 位置；evaluation_payload.questions[] 保存題型、正解與理由通過標準。

Learner response

目前正式題型是選擇、是非與填空。每題都必須提交 value 與 rationale，漏題或格式錯誤視為處理失敗，而非自動判學生答錯。

Validate題號、題數、答案與理由格式完整
Rule judge客觀答案與 correct_answer 正規化比對
LLM judge一次 structured call 判斷每題理由
Merge答案正確且理由正確才是 correct
Persist逐題錯誤、issue types、HT tags 與 input hash
LLM 不負責改寫客觀答案

客觀答案由規則決定；LLM 只判斷理由是否符合研究者為該題寫下的 reasoning_criteria，並回傳史實錯誤、推理錯誤與可選 Historical Thinking 標籤。標籤不是計分本身。

送出後的 Attempt 狀態為 processing → submitted，失敗則為 failed 並可重試。若判題已成功、只在開場生成失敗，judgement_input_hash 會讓重試沿用原判題，避免同一份答案被第二次模型判成不同結果。

Prompt 與 LLM Runtime

一次使用者回覆走一條 canonical prompt pipeline；邏輯上單次生成，技術上可有同模型 retry 或一次 schema repair。

general_prompt所有 Condition 共用的安全、範圍、史實與輸出規則。
independent_2_prompt互動方式：Standard Chat 或 EBL scaffold。
event + task事件情境與已凍結的逐題作答／錯誤資料。
interaction_runtime目前錯誤、EBL 階段、Disclosure level、允許證據與 forbidden aliases。
conversation_history由資料庫取回，依字元預算裁切；不是只保留固定 12 則。
independent_1_prompt呈現身分：中性 AI 或固定歷史人物第一人稱。
runtime_policystructured output、off-topic、答案洩漏與回覆邊界。
user_message只放入 canonical module 一次，不在 provider 外層重複傳遞。
ConditionInteractionRenderer研究控制
01Standard Chat中性 AI 歷史助教不主動要求反思、自我修正
02EBL scaffold中性 AI 歷史助教與 04 共用 EBL/Disclosure policy
03Standard Chat歷史人物第一人稱不主動要求反思、自我修正

Historical Thinking 是四組共用的歷史回應品質基礎，不是額外操弄。EBL 才是 02/04 的互動教學鷹架：發現／認知錯誤 → 分析與反思 → 自我修正 → corrective feedback/resolution。

模型鎖定

LLM_MODEL 是唯一正式 candidate；provider_switching_enabled=false。

輸出驗證

Pydantic schema 驗證；格式失敗可再要求同模型修復一次，未通過不得入庫成正式回覆。

失敗稽核

拒絕輸出與 provider failure 寫入 LLM_REJECTION_LOG_PATH，研究 metadata 另存 DB。

目前刻意暫緩

RAG／向量檢索尚未進正式介入；source_context 模組可以存在，但 runtime 目前不依賴動態檢索。不要在未完成研究設計前偷偷啟用。

身分與權限

兩條入口：Learner JWT 與 Admin shared key。兩者用途不同，不要混成同一種帳號角色。

Learner

以 Authorization: Bearer <Supabase access token> 呼叫。後端驗證 token 後，以 Auth user id 找 participant，並檢查 active、ownership、Condition assignment 與順序。

Admin

以 x-admin-key 呼叫。值只從 HISTOSPHERE_ADMIN_KEY 讀取，缺少時後端拒絕啟動；Frontend 只保存在目前分頁，退出模式即清除。

邊界規則
JWT cache後端只以 token hash 暫存驗證結果 30 秒，不保存原 token。
OwnershipSession、Attempt、Conversation 與 Chat 都比對 JWT owner；另一帳號讀取或寫入應回 403。
Participant archive停止該帳號進入正式 Learner API，但不解除 Auth 綁定，也不刪除既有資料。
RLS目前 public schema RLS 未啟用；安全邊界是 FastAPI + service-role repository。資料庫不得直接暴露給 Learner client。
Public catalogEvent/Condition/Persona 的讀取入口供首頁顯示；Learner view 不回傳 Task 正解與完整評分 payload。

約束與資料完整性

應用程式檢查改善錯誤訊息；Database constraint 才是競態條件下的最後防線。

Constraint / Index保護的風險期待行為
events.canonical_name UNIQUE同一事件被建立兩次名稱正規化後只能有一筆主事件
participants.code UNIQUE受測代號碰撞每個 P-code 唯一
participants.auth_user_id UNIQUE同一 Auth 帳號綁兩位 participant一對一綁定
task_attempts.session_id UNIQUE NOT NULL同一 Session 兩份作答重整與重送都更新／讀取原 Attempt
conversations.session_id UNIQUE NOT NULL同一 Session 兩段對話第二次建立請求回到原 Conversation

研究鏈 FK + NOT NULL / RESTRICTAttempt、Conversation、Message 無法歸屬不得刪除仍被研究紀錄引用的上游資料
Migration 原則

不要改寫已套用 migration，也不要用重設資料庫來代替 migration。新增 timestamped SQL，先處理舊資料相容性，再加入 NOT NULL、FK 或 UNIQUE；任何可能刪除資料的 SQL 都必須先停下來確認。

研究紀錄與可重現性

正式結果不是只看 messages；需要 Session、素材、Prompt、模型與判題一起重播。

Material snapshot

Session 建立時保存 Event、Task、Persona 與 Condition 的內容及穩定 hash，後續素材修改不應改變已發生實驗的解讀。

Prompt snapshot

每次重要 LLM call 保存組裝後 Prompt、modules、hash、provider/model、latency、tokens 與 retry/repair metadata。

Full replay

Admin 可看某 Session 的完整逐字稿、Task 作答與 Judge、訊息數、雙方回合、token 合計與涵蓋率。

Export 規則說明
只輸出正式 Sessionis_admin_test=true 與無法綁定 participant 的孤兒資料不進正式 JSON/CSV。
去識別匯出使用 participant_code，Session/Attempt/Conversation 中的 Auth user_id 清空。
Token 誠實呈現若 provider 未回傳 usage，涵蓋率會低於 100%；不得把缺值當成 0 並宣稱完整。
Hash 可驗證Admin replay 會重算 material/prompt hash，標示是否一致或 legacy missing。

安全修改流程

最小改動不是少驗證，而是只改真正負責該規則的層。

  1. 先確認研究語意

    分清楚這是 UI 文案、工程 contract，還是會改變 Condition／處遇內容的研究決策。

  2. 建立 Git restore point

    大型新增、schema、Prompt 或研究流程改動前先 commit；不要把不相關的使用者變更一起回復。

  3. Database 先寫新 migration

    向後相容地補欄位／資料，再加 constraint。禁止 destructive migration 與 hard delete。

  4. 同步 domain → protocol → repository

    若欄位或操作改變，正式 Supabase adapter 與測試 adapter 都要一致。

  5. 把規則放進 Service/Core

    Endpoint 僅處理 HTTP；Frontend 不能是研究規則的唯一守門員。

  6. 補一個能抓到真實風險的測試

    優先驗證 ownership、cardinality、resume、redaction、material lock 與 export exclusion，不重複寫同義測試。

  7. 以真實 local Supabase 驗證

    Migration 類改動不能只靠 in-memory unit test；至少跑 schema check，流程風險再跑 smoke。

  8. 取得授權後更新文件

    大型改動完成後，依專案規則先詢問研究者，再同步主要文件與 System Map。

故障排查

先判斷是哪一層拒絕，不要以清資料或重建 Session 當第一反應。

後端無法啟動：缺少 HISTOSPHERE_ADMIN_KEY
這是預期的 fail-fast。於本機 .env 設定 key；不要在程式碼加入 fallback。
401：A valid Supabase Auth bearer token is required
Frontend 沒傳 token、token 過期，或誤用 anon key 當使用者 access token。重新登入後再檢查 request header。
403：Participant mapping / ownership / Condition
依序確認 Auth user 是否綁 participant、participant 是否 active、Condition 是否在 condition_list、是否正按 Admin 分派順序，以及 Session owner 是否相同。
409：素材未鎖、Session 已完成或操作重複
409 通常是保護性拒絕，不是伺服器掛掉。查看 detail 後到 Admin 完成素材鎖定、恢復目前 Session，或等待既有 chat operation 完成。
Task 一直顯示 processing
先用同一 attempt_id 查 polling endpoint；GET 會在需要時重新排程仍為 processing 的工作。不要另建 Attempt。查看 backend log 與 rejection audit。
Chat 看似卡住
Learner 訊息已先持久化，串流會回報狀態。檢查 operation endpoint、LLM timeout 與 provider log；使用同一 client_request_id 可安全恢復，不能改內容後重用該 id。
Supabase CLI 顯示 running，但 54321 不通
執行 pnpm dev:repair:supabase-ports 或依 local-development.md 檢查被占用的官方 ports，再重跑 pnpm dev:full。不要任意改 port 逃避衝突。
